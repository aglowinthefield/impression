## Approach

Backfill becomes a published CLI command built from the seed script's discovery and chunking, and the seed script goes: a local dev server is seeded with `impression backfill`, with the server's backfill model set to whatever the developer wants. The server decides everything that costs money (model, price, budget), so a client can't pick Sonnet or skip the budget, and the estimate uses the same price table that records the spend.

Dedupe moves to the server: each backfill piece is stored with a hash of its scrubbed text, unique per owner and project, so "no piece twice" holds across reruns, crashes and two runs at once without client state. The client asks the server for a plan (which pieces are new, already done, or already uploaded live, plus the estimate and budget left), then sends only the new ones.

Old memories are anchored at the commit that was current when their session started, so the existing staleness check catches the ones the code has since moved past. No extra model calls at backfill time.

Setup starts the backfill as a detached process, the same hand-off the pi extension uses at shutdown, because a default run takes 10 to 25 minutes. Progress goes to a small file that `impression status` reads.

Options it beat:
- A server-side queue and worker: a new moving part for a one-off job per person; synchronous requests at three at a time are enough.
- Client-side dedupe state: lost with the config folder, and can't stop two machines backfilling the same repo twice.
- Running backfill extraction on the live model and offering Sonnet as an option: the Self chose Sonnet, and a per-run choice is a knob nobody needs.
- Rechecking every backfilled memory against HEAD at once: a model call per memory up front; anchoring at the old commit gets the same effect through the staleness check as files are touched.

The server half also stands on the memories Persona. Its rules hold: pieces are scrubbed before storage and extraction (memories/I1, AC16), undo retires and leaves superseded memories alone (memories/I3, memories/I4), backfilled memories go live without review (memories/I5), and every backfill call records its operation, tokens and cost (memories/I8, AC17).

Why two tasks: t1 (server) can merge and deploy alone, since no client sends backfill pieces until t2 ships, and its migration and budget check are worth reviewing on their own. t2 needs t1's endpoints.

## Data model and contracts

`sessions` (migration):
- `source text not null default 'hook'`, one of `hook`, `backfill`.
- `piece_hash text`: `pieceHash` from `packages/shared` (sha256 of the trimmed piece text as the server receives it), computed by the server at upload and set for backfill pieces. Unique index on `(owner, project_id, piece_hash)` where `source = 'backfill'`. t2's CLI hashes each piece with the same helper for the plan request. Changed in t1 from "sha256 of the scrubbed transcript": the scrubber lives only in the API, so the CLI couldn't compute that hash, and a scrubber change would make old hashes miss and bill pieces again. Only the hash of the raw text is stored, never the raw text.
- `started_at timestamptz`: when the backfilled session started.
- `extracting_at timestamptz`: a claim on the piece's extraction, so two requests can't both run the model on it. A claim older than 15 minutes (longer than an extract request can take) is abandoned and can be taken over. A request finishing or failing sets `extracted_at` or clears `extracting_at` only while `extracting_at` still equals the claim it took, so a request whose claim expired can't mark the piece extracted or drop its replacement's claim. Added in t1: holding a row lock across the model call instead would tie up a pooled connection per piece in flight. Extraction writes its memories, proposals and events in one transaction (one piece's at a time per person, so each piece's dedup sees the last one's memories) that first locks the piece's row and checks `extracting_at` still equals its claim, and sets `extracted_at` in the same transaction; a request that lost its claim writes nothing. The model call has a 5-minute deadline, well under the claim window: past it the call is aborted and nothing is written (added in t1, after a request whose claim expired was seen writing a second set of memories). No transaction, row lock or advisory lock is held across a model or embedding call: the transcript call, each item's embedding, repeat check and dedup check (and a merge's embedding) all run first, outside any transaction and under the same deadline, and the write transaction makes only database writes. An item's dedup check also sees what the piece's earlier items will write. When another of the person's pieces was written after a piece's dedup checks began (the count of their extracted backfill pieces changed), the write transaction writes nothing and the dedup checks run again, up to 3 times before the request fails and gives the piece back (changed after t2's review, from embeddings and dedup calls inside the write transaction).
- `extracted_at timestamptz`: set when extraction finishes, so a piece stored but not extracted (a failed or interrupted run) is sent to extraction again.

Server settings: `BACKFILL_MODEL` (default `claude-sonnet-5-5`), `BACKFILL_BUDGET_USD` (default 10). The server refuses to start when `BACKFILL_MODEL` has no price in `usage.ts` (Ollama models count as free), since its spend would read as $0. Added in t1. Spend is the sum of the person's `usage_events` with operation `backfill`. The owner handover (`owner:rename`) moves a person's `usage_events` with their sessions, filling in the new name's GitHub user, so their spend doesn't start over; a backfill piece both names stored is kept once, the extracted copy if only one is (added in t1).

`POST /backfill/plan` body `{ project, pieces: [{ sessionKey, hash, chars }] }` (`project` is the key, or `{ key }`; `sessionKey` is optional) returns `{ pieces: [{ hash, status: "new" | "done" | "live" }], estimateUsd, budgetUsd, spentUsd, model }`. `live` means the hooks already uploaded a session with that `sessionKey` for this owner. The estimate prices the new pieces' characters at about 4 per token plus the extraction prompt, at the backfill model's prices, plus 2,000 output tokens each.

`POST /sessions` accepts `source: "backfill"`, `startedAt` and `commitSha`. A backfill piece whose hash exists returns the existing row with `duplicate: true` and `extracted` (whether `extracted_at` is set). No one-day window for backfill.

`POST /sessions/:id/extract` on a backfill session: refuses with 402 `{ error: "backfill budget used up", spentUsd, budgetUsd }` when recorded spend, plus the estimates of the person's other unexpired claims, plus this piece's estimate (the plan's per-piece estimate, on the stored transcript's length) would pass the budget. The check and the claim run in one transaction holding a per-person advisory lock, so pieces sent at once can't share the same headroom (changed in t1 from "spend has reached the budget", which let four pieces at once all pass). Spend and the other claims are read in one statement, and a piece's usage rows are written before its claim is cleared, so a piece finishing meanwhile counts as one or the other, never neither (changed after t2's review); otherwise extracts with `BACKFILL_MODEL`, records usage as `backfill`, sets `extracted_at`, and returns `{ saved, updated, costUsd }`: `saved` new memories, `updated` existing ones it superseded or merged into, read from the session's memory events. A piece already extracted returns its earlier counts without a model call, as `{ saved, updated, costUsd: 0, alreadyExtracted: true }`. While another request is extracting the piece it returns 409 `{ error: "piece is being extracted" }` without a model call; the client counts the piece as not sent, and the next run's plan shows it done. A request whose claim expired and was taken over before its model call returned gets the same 409, writes nothing and leaves the piece to the new claim (added in t1). Spend passes the budget only by what pieces cost beyond their estimates.

`POST /backfill/undo?project=<key>` retires the caller's live memories that extraction wrote from a session with `source = 'backfill'` in that project and filed in that project (or as the caller's own practices), with a `memory_events` row each, and returns `{ retired }`. Extraction's authorship is read from its proposal: the memory has a proposal from that session no older than itself (a memory extraction only deduped onto is older). A manual memory naming a backfill session, and memories extraction filed in another repo the session touched, are left alone (both added in t1). Superseded memories are left as they are. A project the caller can't see, or that doesn't exist, gets 404 `{ error: "project not found" }`, as the other project routes answer (changed in t1 from `{ retired: 0 }` for an unknown project, so someone who lost repo access can't retire memories others there see).

CLI:
- `impression backfill [--repo <path>] [--since <date>] [--limit <n>] [--agents pi,claude,codex] [--yes] [--dry-run] [--undo]`. Discovery and chunking come from the seed script, which is deleted along with its `seed` package script and its README section (replaced by one for backfill).
- The repo's dirs are the checkout plus each worktree's `git rev-parse --show-toplevel` (with a separate git dir, git lists the git dir as the main worktree; it has no top level and is left out). Changed in t2 from the git common dir's parent.
- An entry in a transcript store that can't be stat'ed or read (a dangling or unreadable link, a file without read permission) is skipped, and the rest of every agent's sessions are still listed (added after t2's review).
- Sessions whose file changed in the last hour are skipped by the file's mtime, before anything in the file is read. Only pi and Claude Code files in the repo's transcript folders are counted in the plan's "changed in the last hour"; a Codex rollout's repo is known only from its contents, so a running one is skipped uncounted (changed in t2).
- Each piece's `commitSha` is `git rev-list -1 --first-parent --before=<session start> HEAD`, or the repo's first commit when the session predates it. Each project candidate's `headSha` (another repo the session touched) is found the same way in that repo, not its HEAD (added in t2). `--first-parent` added after t2's review: a side branch's commit merged after the session started wasn't on the branch then.
- Budget fitting compares whole millionths of a dollar, not float dollars (added in t2).
- The plan prints the session count, piece count and estimate even when no piece fits the budget left, and when nothing is new, before "Nothing new to backfill." (added in t2).
- A session whose cwd's own git top level (or, when the cwd is gone, its nearest existing ancestor's) is a different repo nested under the repo's dirs is left out: it belongs to that repo (added in t2).
- With instruction sharing on, the instruction files sent with each extract are read from the backfilled repo's checkout, not the directory the command ran in (added in t2).
- The run's final cost is the sum of the `costUsd` the server returned for this run's pieces. Changed in t2 from the person's spend after the run less their spend at the plan, which counted another repo's backfill running at the same time; a piece the server bills but answers with an error is no longer counted. "Sessions read" counts every session the run started a piece of, whatever the piece's outcome (changed in t2 from sessions with a successful piece).
- Lock: `~/.config/impression/backfill/<project hash>.lock` holding the pid and, on Linux, the process's start time from `/proc/<pid>/stat` (`<pid> <start>`; pid only elsewhere). A lock whose pid is running but started at another time belongs to a process that reused the pid, and is stale (start time added after t2's review). It is written whole under a unique name and hard-linked into place (an exclusive create, so it is never read half-written). A lock whose pid is gone is moved aside under a unique name, removed only if the moved file is the one found stale (same inode and text), and put back otherwise; then the create is retried. Changed in t2 from read-then-unlink, which let two runs both win.
- Undo takes the same lock, asks before it retires (`--yes` skips the question; without a terminal it needs `--yes`), and `--dry-run --undo` sends nothing (added in t2).
- Progress: `~/.config/impression/backfill/<project hash>.json` with `{ total, done, saved, updated, failed, notSent, costUsd, startedAt, finishedAt }`, written after each piece; `impression status` prints it for the current repo while unfinished and once after it finishes, even when its server request fails (the error follows on stderr). It clears the file after printing it (changed after t2's review, from clearing before the line was printed), and only when a fresh read still has the `startedAt` and `finishedAt` it showed, so it can't clear a new run's progress (added in t2).
- Retry: one retry on a 5xx or timeout; a 402 stops the run. Once a 402 is seen no piece starts an upload, extract or retry; a piece uploaded meanwhile is counted not sent and goes again next run (added in t2).
- Setup: after the existing steps, if signed in, interactive, and the cwd is in a git repo with new pieces, it shows the plan and asks; on yes it hands off `impression backfill --yes` detached, waits for the child's `spawn` or `error` event, and says it started or that it couldn't (with `impression backfill --repo <checkout>` to run by hand), then exits either way (changed in t2). Whenever setup skips the offer in a repo (no terminal, not signed in, or a dry run) it prints `impression backfill` as the command to run (changed after t2's review: not signed in, it printed nothing).

## Invariants

- agents/I1: holds. A failed discovery, plan or upload in setup prints one line and setup finishes; backfill is never run from a hook, so no agent session sees it.
- agents/I2: holds. Nothing is added to the prompt path.
- agents/I3: holds. Setup's backfill runs detached and outlives setup. Running sessions are skipped (changed in the last hour), so no transcript is read while an agent appends to it.
- agents/I4: holds. Backfill is a CLI command, not a hook, and acts in no agent.
- agents/I5: holds. Setup starts the backfill with the bundled CLI and node, as the other hand-offs do.
- agents/I6: holds. The project key comes from the repo the same way the hooks resolve it, so worktree and subdirectory sessions land in one project.
- agents/I7: holds. Not signed in, `impression backfill` says so and exits; setup offers backfill only after sign-in.
- agents/I8: holds. The offer changes no agent config.
